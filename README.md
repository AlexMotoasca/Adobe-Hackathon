# MindMarket
Database-backed creative analysis MVP. The frontend uses the endpoints in [backend/API.md](backend/API.md).

## Run
Install backend dependencies and configure backend/.env.local. Start PostgreSQL at the configured DATABASE_URL and apply migrations with npm run db:migrate from backend.

On Windows run start-fullstack.cmd. It starts the frontend on port 3000, backend on 3001, and analysis worker. Stop existing instances before launching. Open http://localhost:3000.

## Workflow
- The dashboard lists only analyses returned by PostgreSQL, with pagination.
- Create a campaign using the seven required context fields.
- Upload an image ad (PNG, JPEG or WebP, 4 MiB maximum) or a video ad (MP4, WebM or MOV, up to 10 minutes). The browser samples a video into a labelled 9-frame storyboard. The opening seconds are sampled closely and the final frame is included, and only the storyboard is uploaded. Audio is not analysed. Category research collects web excerpts and YouTube audience comments automatically; no CSV is required. The frontend accepts only the creative image; the legacy review-upload API remains available for existing integrations.
- Start analysis and follow backend stage updates every 2.5 seconds.
- Completed reports show generated recommendations, personas, evidence assessments, source reviews and limitations.
- Failed analyses can be retried; draft and failed analyses allow replacement uploads.
- Loading and failure messages reflect actual requests. No synthetic progress or fallback reports are generated by the frontend.

There is no login or persisted profile API in this MVP. Existing database records, including engineering test records, remain visible. No readiness score or monetary savings are invented.

## Automatic category research

Set `TAVILY_API_KEY` and `YOUTUBE_API_KEY` in `backend/.env.local`, enable YouTube Data API v3 for the Google API key, and restart the worker. Keys stay on the backend. Either source can run independently. Missing keys, quota errors, disabled comments and empty results appear as coverage warnings in the report; the analysis can still complete with explicitly limited evidence.

Optional `GROQ_RESEARCH_MODEL` selects a separate Groq model for query planning and evidence filtering (for example `openai/gpt-oss-20b`); if unset it uses `GROQ_TEXT_MODEL`. Model availability and free-tier quotas depend on the account. Groq performs reasoning here; it is not treated as a Google search API or a source of invented reviews.

Each new analysis makes at most three Tavily searches (five excerpts each), one YouTube video search (three videos), and three top-level comment requests (eight comments each). No transcripts or full reply trees are fetched. Search text is based on the inferred category, market and language, rather than solely on the product name. Tavily searches exclude Reddit until appropriate access is arranged. Web excerpts are labeled separately from audience comments. Source text is deduplicated, bounded and filtered for relevance with Groq before persona evaluation.

Research is checkpointed in the existing analysis outputs, so a resumed analysis reuses the same evidence. No database migration is required. Caching across separate analyses is not implemented. To refresh research, create a new analysis or replace an upload on a draft/failed analysis to reset its checkpoints.

Evidence filtering runs in batches of six sources with bounded output and source-ID validation. Failed batches are excluded with a visible reason while successful batches are retained; free-tier rate limits can therefore result in partial coverage.

Reports show an evidence summary at the top (retained sources, sources supplied to personas, and sources cited in objections), or a prominent warning when no customer evidence was used. They also show source links, retrieval time, available publication dates, research coverage, buying criteria and supported competitor mentions. These are sampled opinions and excerpts, not verified current prices, representative market statistics, or verified ownership. Missing evidence never becomes a claimed product defect. Current-price feeds and numeric persona ratings are not part of this implementation.

API references: [Tavily Search](https://docs.tavily.com/documentation/api-reference/endpoint/search), [YouTube search](https://developers.google.com/youtube/v3/docs/search/list), [YouTube comments](https://developers.google.com/youtube/v3/docs/commentThreads/list).

## Sign in with Google

The landing page (`/`) is public and shows how many marketers have signed up. The dashboard, analysis pages and every `/api/analyses` route need a signed-in user. Each user sees their own reviews; reviews created before sign-in existed stay visible to every signed-in user.

**Setup (one time):**
1. In Google Cloud Console, open **APIs & Services → Credentials → Create credentials → OAuth client ID**. Choose **Web application**. (Configure the OAuth consent screen first if prompted; External with yourself as a test user is enough for local use.)
2. Under **Authorized redirect URIs**, add `http://localhost:3000/api/auth/google/callback`.
3. Add the client ID and secret to `backend/.env.local`:
   ```env
   GOOGLE_CLIENT_ID=...apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=...
   APP_ORIGIN=http://localhost:3000
   ```
4. Apply the database migration (`npm run db:migrate` in `backend`) and restart the backend.

**How it works:**
- The flow is an OAuth 2.0 authorization-code flow with PKCE and a `state` check, both held in a short-lived HttpOnly cookie.
- Only verified Google emails are accepted. The ID token's issuer, audience and expiry are checked.
- Sessions are stored server-side, and only a SHA-256 hash of the token is kept in the database. The browser holds the raw token in an HttpOnly, SameSite=Lax cookie (`Secure` on https) that lasts 30 days.
- After sign-in, only relative paths are accepted as redirect targets.

**Endpoints:**

| Endpoint | What it does |
|---|---|
| `GET /api/auth/google` | Starts sign-in |
| `GET /api/auth/google/callback` | Google redirects back here |
| `GET /api/auth/me` | Current user, or 401 |
| `POST /api/auth/logout` | Ends the session |
| `GET /api/stats` | Public: `{ users, googleConfigured }` |

## Video playback and transcripts

- For a video, the browser uploads three things:
  - a 9-frame storyboard, which the vision model reads
  - the original file, up to 200 MB, for playback in the report
  - a 16 kHz mono audio track, which Groq Whisper transcribes once at upload time
- Videos are stored on local disk in `backend/.local/media` (gitignored; set `MEDIA_DIR` to change it). They are served with HTTP range requests, so the player can seek, and are copied when an analysis is rerun.
- In the report, every timestamp is clickable and jumps the player to that moment. This covers storyboard frames, transcript lines, and times mentioned in recommendations such as "at 1.5 s".

## Rate limits: same-key model fallback

Groq quotas are counted per model. When a text model reaches its limit or asks for a cooldown longer than 20 seconds, the request continues on the next model **on the same key**. The default order is `openai/gpt-oss-20b`, then `qwen/qwen3.8-27b`; override it with `GROQ_FALLBACK_MODELS` (comma-separated). Keys are never switched. If every model on a key is exhausted, the analysis fails with a resumable error, as before.

## Feedback approach

The analysis gives feedback on the ADVERTISING, not a verdict on the product. Five simulated audience members review each ad, each with a different buying psychology:
- the skeptic, who needs trust and proof
- the System-1 scroller, who decides in about 3 seconds
- the value seeker
- the aspirational, identity-driven buyer
- the System-2 planner

Each one reports what works on them, what loses them, and up to 3 suggestions. Each suggestion names the psychological principle it uses, for example social proof or loss aversion. For video ads, they also judge the opening hook, the pacing and the ending. The creative-director summary then keeps the strengths and picks the 3 highest-impact changes. The model's suggested changes are kept as written. Example copy that states numbers, prices, rankings, guarantees or certifications is replaced with a placeholder template, so the report never publishes unverified claims.

## Speed and retrieval

- The ad's image is read while the web research runs, because neither step needs the other's result. Tavily queries, YouTube comment threads, and the two providers are all fetched at the same time. Request limits are the same as before.
- Customer themes are generated while the personas run.
- Findings with no cited source become `hypothesis` directly, with no model call. Only cited findings go to evidence validation.
- Text sent to the evidence filter is trimmed to 1,000 characters per source, and customer-theme input to 600, so prompts are smaller.
- Persona evidence retrieval ranks sources with BM25 and ignores stopwords. Sources the filter has already validated get a boost. Sources from the same site or video, and near-duplicate wording, are penalized so each persona sees a range of views. The search query combines the persona's focus, the category, the comparison group, and the ad's own claims, benefits and offer. Excerpts are still contiguous original text, now starting on a sentence boundary.

### Persona inputs and team routing

New persona calls receive at most six source excerpts of 900 characters each (5,400 evidence-text characters total), selected by their specific priorities. Excerpts are contiguous original text, never generated quotations. Full sources remain in reports and evidence validation. Cached personas retain their original source IDs when resumed.

Default `GROQ_PERSONA_ROUTING=single` preserves sequential execution on the existing key. For an authorized team quota arrangement, configure these server-only values in `backend/.env.local`:

```env
GROQ_PERSONA_ROUTING=team
GROQ_API_KEY=your_existing_key
GROQ_TEAM_2_API_KEY=second_team_key
GROQ_TEAM_3_API_KEY=third_team_key
```

Fixed assignments run concurrently: key 1 handles skeptic; key 2 handles impulsive then bargain; key 3 handles quality then rational. At most three persona requests run simultaneously, with one active request per assignment. Research filtering and evidence-validation batches use fixed round-robin assignments across the three keys (batches 1/4/7 on key 1, 2/5 on key 2, 3/6 on key 3). Each key processes its batches in order; different keys run in parallel. Research filtering uses GROQ_RESEARCH_MODEL on each key; validation uses each assigned persona model. Planning and image interpretation stay on the main key; consumer insights run on key 2 and the final synthesis on key 3, which keeps key 1 from running out of quota first. Retrying a saved analysis preserves prior research; use Rerun analysis for fresh collection with the new assignments. Optional `GROQ_TEAM_1_MODEL`, `GROQ_TEAM_2_MODEL`, and `GROQ_TEAM_3_MODEL` override persona models; otherwise all use `GROQ_TEXT_MODEL`. Team routing requires all three keys and rejects duplicate key values. Separate keys do not establish separate organization quotas or authorization to combine quotas.

Requests retry on their assigned key only. They never switch keys after throttling; long provider cooldowns fail with a resumable error. Successful persona checkpoints are saved serially, and failed runs wait for in-flight assignments to settle before reporting failure. Restart the worker after changing configuration; its startup line shows whether team routing is active. Run `npm run check:provider -- --models-only` from backend to confirm all three keys can reach the configured models without spending tokens. No speedup is claimed until measured with the configured accounts.
